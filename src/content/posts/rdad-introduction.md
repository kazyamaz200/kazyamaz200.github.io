AIコーディングエージェントに開発を任せるとき、何を指示すればよいのだろうか。

実装する機能を詳しく説明する。使用するライブラリを指定する。テストを必ず実行するように指示する。

どれも大切だが、長時間にわたって自律的に開発を進めるエージェントには、もう少し上位の判断基準が必要だと感じている。

- どこまで設計するのか。
- どこまで実装するのか。
- どの程度テストするのか。
- そして、何をもって完成とするのか。

こうした判断をエージェント任せにすると、必要以上に複雑な実装が生まれたり、統合テストの修正ループから抜け出せなくなったりする。

そこで考えたのが、**RFC-Driven Agentic Development（RDAD）**、日本語では「RFC駆動型エージェント開発」だ。

本記事では、RDADの考え方と、実際の開発への取り入れ方を紹介する。

## RDADとは何か

RDADは、RFCを起点として、コーディングエージェントが設計・実装・検証を自律的に進めるための開発原則である。

ここでいうRFCは、**Request for Comments** の略だ。

インターネット標準やOSS開発などで用いられている、提案を文書化し、レビューや議論を経て方針を決める仕組みを指す。

RDADでは、RFCを単なる提案書としてではなく、開発の目的・範囲・受入条件を定義する起点として使用する。

そして、次の考え方を重視する。

> **Think at boundaries. Build simply. Verify by risk. Finish predictably.**
>
> 境界は深く考え、実装はシンプルに、検証はリスクに応じて、確実に完成させる。

なお、RDADは既存の標準化された開発方法論ではない。RFCを用いた開発や契約テスト、リスクベーステストなどの考え方を、自律的なコーディングエージェントの運用に合わせて組み合わせた、個人的な提案である。

## RDADを構成する6つの原則

### 1. Contract First — 境界を先に決める

RDADで最も重視している原則だ。

複数のコンポーネントが連携するシステムでは、各コンポーネントの内部実装が正しくても、システム全体が正しく動作するとは限らない。

例えば、次の3つのコンポーネントを持つシステムを考えてみる。

- **API**：処理要求を受け付ける
- **Worker**：非同期で処理を実行する
- **Database**：処理結果と状態を保存する

ここで重要なのは、Workerの内部処理をどれだけ丁寧に実装するかだけではない。

APIが処理を受け付けた時点で何を保証するのか。Workerが失敗した場合にどの状態を返すのか。Databaseへの保存が失敗した場合、誰が再試行するのか。

こうしたコンポーネント間の約束が曖昧なまま実装すると、統合段階で問題が発生しやすい。

RDADでは、予備設計の段階で以下を定義する。

- 責務とデータの所有者
- API・イベント・データ形式
- 成功・失敗条件と状態遷移
- タイムアウト・再試行・重複実行
- 部分失敗時の状態と復旧の責任
- 契約を検証する方法

ただし、すべての例外を網羅する必要はない。

要求を実現するために必要な契約と、障害時の影響が大きい境界を優先する。

また、既存コンポーネントの仕様を推測で決めないことも重要だ。ドキュメントに加えて、実際のコードやテストも確認する。

### 2. Minimal Sufficient Implementation — 最小十分な実装

コーディングエージェントは、要求された内容を超えて、将来の拡張性や汎用性まで考慮した設計を提案できる。

それ自体は強みだ。

しかし、あらゆる拡張可能性に備えた設計が、現在のプロジェクトにとって適切とは限らない。

RDADでは、RFCの受入条件を満たす、最も単純で保守可能な実装を優先する。

例えば、現在必要な機能が一つだけなのに、将来さまざまな実装を差し替えられるプラグイン機構を先に構築する必要があるだろうか。

将来の要求が明確なら、そのための設計は合理的かもしれない。

一方、まだ存在しない要求に備えて大きな仕組みを構築することは、実装・テスト・保守の負担を増やす可能性がある。

重要なのは、拡張性を否定することではなく、現時点で必要な拡張性を見極めることだ。

もちろん、シンプルさを理由にセキュリティ、データ保護、整合性などの必須要件を省略してはならない。

### 3. Risk-Based Verification — リスクに応じて検証する

テストは多ければ多いほどよいのだろうか。

必ずしもそうではないと思う。

重要なのは、どれだけ多くのテストケースを作ったかではなく、失敗した場合の影響が大きい振る舞いを十分に検証できているかだ。

例えば、認証、権限、データ損失、冪等性、重要な状態遷移などは、特に注意して検証する必要がある。

一方で、内部の関数呼び出し順序や、変更される可能性の高い実装詳細まで厳密に固定することには慎重でありたい。

RDADでは、テストを次のように考える。

| テスト | 重視すること |
| --- | --- |
| Unit | 主要な正常系、重要な境界値、代表的異常系 |
| Contract | コンポーネント間の入出力、状態、エラーの整合性 |
| Integration | 実コンポーネントの接続と協調動作 |
| E2E | RFCの受入条件を満たすこと |

特に、Unit Testを大量に整備してから最後にIntegration Testを実施する進め方は見直したい。

重要なコンポーネント間の接続は、実装の早い段階から確認する。

最終的な統合テストを、初めてシステム全体を動かす場にしないことが重要だ。

#### FixtureとMockは必要十分に

AIによるテスト生成では、FixtureやMockを過剰に構築しないことも意識したい。

例えば、単純な入力データのテストに、多数の状態を持つ共通Fixtureや複雑な初期化処理を用意する必要はない。

Fixtureは必要な状態だけを持つ小さなものを基本とする。

Mockは外部境界や制御が難しい依存関係を中心に使用し、内部の実装構造を不必要に固定しない。

そして何より、**Mockを使ったテストの成功と、実コンポーネント間の契約成立は別物だ**ということを忘れない。

### 4. Complexity Budget — 複雑性にも予算を設ける

機能を追加すれば、通常は何らかの複雑性が増える。

これは避けられないが、増やす複雑性には根拠が必要だ。

RDADでは、新しい抽象化、共通ライブラリ、設定項目、Fixture基盤などを追加する前に、次のことを考える。

1. それがなければ受入条件を満たせないか
2. 既存の仕組みで実現できないか
3. 追加する複雑性に見合う具体的な利益があるか
4. 実装・テスト・運用の負担を不必要に増やさないか

これをComplexity Budget、複雑性の予算と呼んでいる。

数値による厳密な予算管理ではない。

新しい仕組みを追加する前に、その必要性を説明するという意思決定のルールだ。

不要な共通化や過剰な汎用化を抑えることが目的であって、適切な抽象化を禁止するものではない。

### 5. Bounded Iteration — 終わらない修正ループを防ぐ

自律的なコーディングエージェントにとって、特に重要だと考えている。

統合テストで不具合が発見された場合、エージェントは修正を試みる。

改善しなければ別の修正を行い、再びテストする。

この反復が必要な場面も多い。

しかし、設計の前提が間違っているのに、コードの修正だけで解決しようとすると、試行錯誤が長期化することがある。

RDADでは、不具合を次のように分類する。

- 実装不備
- コンポーネント間の契約不一致
- 設計不備
- 環境・設定・データ起因
- 新たな要求やRFCの範囲外

そして、修正は次の順序で行う。

> 原因の仮説 → 最小限の修正 → 対象を絞った再テスト → 関連する回帰テスト

さらに、自律的な反復を見直す目安を設ける。

同じ不具合に対する修正が2回改善につながらなければ、原因分析に切り替える。

統合テストの修正サイクルが3回に達したら、状況と設計前提を再評価する。

これらの回数は、テストを打ち切るための絶対的な制限ではない。

同じ問題を無制限に追いかけず、いったん立ち止まって判断し直すためのシグナルである。

重大な問題が未解決なら、完了扱いにせずBlockedとして明示する。

### 6. Evidence-Based Completion — 証拠に基づいて完成を判断する

最後の原則は、何をもって開発完了とするかだ。

エージェントが「実装しました」と報告することと、実際に要求された機能が成立していることは同じではない。

RDADでは、RFCの受入条件と検証結果を根拠として完了を判断する。

最低限、次の情報を確認する。

- 実装した機能と変更範囲
- 受入条件ごとの達成状況
- 実施したテストと結果
- 実コンポーネントとMockの使用状況
- 未解決事項と残るリスク
- 別Issueに切り出した改善事項

未実施のテストを成功と報告してはいけない。

また、追加できる改善が残っているからといって、いつまでも完了を先送りする必要もない。

RFCの受入条件を満たし、重大な未解決問題がなければ、今回の開発を完了とし、将来の改善は別Issueで管理する。

## RDADの開発フロー

これらの原則を実際の開発に適用する際は、次のフローを使用する。

> RFC → 予備設計 → 実装計画 → 実装・段階的検証 → 統合・受入検証 → 完了

### Step 1：RFC

何を、なぜ作るのかを定義する。

要求だけでなく、対象外の範囲と受入条件も明確にする。

### Step 2：予備設計

コンポーネントの責務と契約を整理する。

複数コンポーネントにまたがる変更では、ここに **Contract Gate** を設ける。

Contract Gateでは、少なくとも次の事項を確認する。

- [ ] コンポーネントの責務とデータの所有者
- [ ] 主要な入出力と状態遷移
- [ ] 成功・失敗と主要異常系の扱い
- [ ] 再試行・復旧の責任分担
- [ ] 契約を検証する方法
- [ ] 最低限のE2E受入シナリオ

重要な契約が未確定なら、実装計画の確定前に解決する。

### Step 3：実装計画

コンポーネントごとに大量の実装を進めるのではなく、可能な限り動作検証できる機能単位に分割する。

例えば、API、Worker、Databaseをそれぞれ最後まで実装してから結合するのではなく、最小限の処理が最初から最後まで通る状態を早期に作る。

このような縦断的な実装によって、コンポーネント間の問題を早く発見できるようにする。

### Step 4：実装・段階的検証

合意済みの契約に従い、最小十分な実装を進める。

小さな単位でテストと結合確認を行い、重大な契約不一致が見つかった場合は、必要に応じて予備設計へ戻る。

### Step 5：統合・受入検証

RFCの受入条件を中心にシステム全体を確認する。

不具合修正は原因に基づいて行い、修正を繰り返しても収束しない場合は再評価する。

### Step 6：完了

受入条件と検証結果に基づき、完了可否を判断する。

追加改善は原則として別Issueへ切り出し、完了条件を際限なく拡張しない。

## Tracking Issueで開発を一貫して管理する

RDADでは、RFCから検証までをGitHubの一つのTracking Issueで管理する方法を想定している。

進捗を単純な「作業中」「完了」だけで管理せず、次の状態を区別する。

| 状態 | 意味 |
| --- | --- |
| Design Complete | Contract Gateを通過した |
| Implementation Complete | 計画した実装が完了した |
| Verification Complete | 必須の検証と受入条件を満たした |
| Blocked | 完了を妨げる問題が残っている |
| Follow-up | 対象外の改善を別Issueに記録した |

特に重要なのは、**Implementation CompleteとVerification Completeを分けること**だ。

実装が終わったことと、システムとして成立していることは違う。

また、追加改善を次々にTracking Issueへ取り込むと、いつまでも完了しなくなる。

RFCで合意した受入条件を維持し、新たな要求は別途管理する。

## すべての変更にRFCが必要なわけではない

ここまで読むと、RDADは少し大げさな開発プロセスに見えるかもしれない。

しかし、軽微なバグ修正や、既存の契約を変更しない局所的な実装まで、すべてRFCから始める必要はない。

例えば、単純な表示修正ならIssueと受入条件だけで十分だろう。

一方、複数コンポーネントにまたがる変更、公開APIの変更、状態遷移やデータ整合性に影響する変更では、RFCとContract Gateを活用する価値が高い。

重要なのは、プロセスそのものを目的化しないことだ。

RDADを導入した結果、設計資料やレビュー項目が過剰に増えてしまったら本末転倒である。

開発プロセスにも、Minimal Sufficient Implementationを適用する。

## コーディングエージェントでどう使うか

RDADは特定のモデルやサービスに依存しない。

CodexやOpenCodeなど、さまざまなコーディングエージェントに適用できる開発原則として考えている。

導入するときは、まず共通の開発規約として `RDAD.md` を用意し、エージェントから参照できるようにする。

そのうえで、新しい機能の開発を依頼するときに、次のように指示する。

```text
この開発はRDADの原則に従って進めてください。

まずRFCで要求と受入条件を確定し、複数コンポーネントにまたがる部分については予備設計でContract Gateを実施してください。

実装は必要十分な範囲に限定し、重要な契約と統合シナリオを早期に検証してください。

不具合修正が収束しない場合は無制限に再試行せず、原因と残課題を整理して報告してください。
```

さらに、実装完了時には受入条件とテスト結果を必ず報告させる。

これだけでも、単純に「この機能を完成させて」と指示する場合とは、開発の進め方が変わるはずだ。

## これから検証したいこと

RDADはまだv0.1の段階だ。

今後、実際の開発に適用しながら、次の点を評価していきたい。

- 統合テストで発見される契約・設計起因の不具合は減るか
- 不具合の修正サイクルは減るか
- 不必要な抽象化やFixtureの構築は減るか
- Tracking Issueが完了するまでの作業量やトークン消費は減るか
- 受入条件の達成率を維持できるか

もちろん、タスクの難易度やモデル、推論強度、実行環境が違えば単純比較はできない。

まずは実際の開発記録を蓄積し、効果が確認できた原則を残し、うまくいかない部分は見直していくつもりだ。

RDADそのものも、固定された完成形ではなく、継続的に改善していく対象として扱いたい。

## おわりに

AIエージェントの能力が高くなるほど、人間がコードの細部を指示する必要は減っていくのかもしれない。

その一方で、何を作るべきか、何を作らないべきか、どの品質を保証すべきかという判断の重要性は、むしろ増していくように感じている。

RDADは、AIにもっと多くのコードを書かせるための仕組みではない。

AIが自律的に開発を進める中でも、要求と設計の意図を保ち、必要十分な実装を、検証可能な形で完成させるための原則だ。

最後に、RDADの考え方をもう一度。

> **Think at boundaries. Build simply. Verify by risk. Finish predictably.**

そして、開発の完了については、次のように考えている。

> 完成とは、追加できる機能やテストがなくなることではない。定義された要求が、検証可能な形で満たされることである。
