最近、「脆弱性」という言葉をニュースで目にする機会が増えたように感じる。

ソフトウェアエンジニアにとっては馴染みのある言葉だが、そうでない人にとっては「ハッキング」「情報漏えい」と一緒に語られる、少し専門的な言葉だったのではないだろうか。

その距離感が、AIによって変わり始めているように思う。

AIに尋ねれば、難解な脆弱性情報をかみ砕いて説明してくれる。コード解析や調査を支援することもできる。一方、同じ技術が攻撃の探索や試行にも使われ始めている。

これを私は、仮に**「脆弱性の民主化」**と呼んでみたい。

ただし、一般の人が脆弱性を理解するようになったという統計的な結論ではないし、AIさえあれば誰でも高度な攻撃ができるという意味でもない。脆弱性を理解し、探し、対処するために必要だった専門的な作業の一部が、より身近になっているのではないかという、現時点での個人的な観察だ。

この変化を、攻撃と防御の両方から考えてみたい。そして開発者として、ひとつ提案したいことがある。

**AIがコードを書く速度を上げたのなら、コードの品質と安全性を確かめる仕組みも、開発初日から作ろう。**

## 「脆弱性がある」と「攻撃される」は違う

まず、言葉を整理しておきたい。

脆弱性は、ソフトウェアの実装、設計、設定などに存在する、悪用され得る弱点だ。攻撃は、その弱点を利用しようとする行為。そして、実際に情報漏えいやサービス停止などが発生すれば、被害やインシデントとして問題になる。

つまり、脆弱性の存在、攻撃の成立、被害の発生は同じことではない。

技術者にとっては当然に見える区別も、ニュースの見出しだけでは伝わりにくい。逆に、脆弱性が公開されたからといって、深刻な影響を一律に否定できるわけでもない。

AIはこの区別を学ぶ手助けになる。同時に、攻撃の準備に必要な情報収集も効率化し得る。ここが厄介であり、興味深いところだ。

## 同じAIが、攻撃にも防御にも使われる

2026年10月23日更新のJPCERT/CCの注意喚起には、AIを利用したペネトレーションテスト基盤を悪用する攻撃試行の事例が追記された。インターネット上のWebアプリケーションに対し、脆弱性の探索や悪用の試行が確認されている。

また、NICTが10月13日に公表した「A2B攻撃」も示唆的だ。公開されたAndroidアプリを解析し、その先にあるバックエンドのAPIやサーバーを狙う手法で、NICTはAIによって解析や脆弱性探索が効率化される可能性にも注意を促している。

ここで重要なのは、「アプリに見えている画面が安全なら、裏側も安全」というわけではないことだ。利用者に公開されていないつもりのAPIであっても、認証・認可や入力検証が不十分なら攻撃対象になり得る。

一方、防御側でも、AIはコードレビュー、脆弱な依存関係の調査、テストの作成、修正案の検討などを支援できる。

| 同じ技術的な作業 | 攻撃側の利用 | 防御側の利用 |
| --- | --- | --- |
| コードやアプリの解析 | 弱点や攻撃経路の探索 | 欠陥や設計上の問題の発見 |
| APIの振る舞いの確認 | 認可不備などの悪用可能性の探索 | 認証・認可・入力検証の確認 |
| OSS依存関係の調査 | 既知の脆弱性を手掛かりにする | 影響を受けるコンポーネントの特定 |
| 自動的な試行と検証 | 攻撃工程の効率化 | 修正と回帰テストの効率化 |

攻撃と防御に使われる道具が似ていても、目的、権限、責任はまったく違う。AIの能力が広がるほど、どこまでが正当な検証で、誰が何を守るのかという境界が重要になる。

## Brotliの脆弱性が教えてくれること

最近の例として、圧縮ライブラリBrotliの脆弱性 CVE-2026-111497 がある。ニュージーランドのNCSCは2026年10月29日、攻撃者が細工した圧縮データの処理によってメモリ情報の漏えいやコード実行につながる可能性があり、実際の悪用も把握していると注意喚起した。

Brotliは単独のアプリケーションとしてだけでなく、ランタイム、フレームワーク、コンテナの中に間接的に含まれることもある。

ここで「使っているライブラリに重大な脆弱性がある」と聞いたら、何を判断すればよいだろう。

- 対象となる実装・バージョンが本当に含まれているか。
- 問題のある展開処理を実際に利用しているか。
- 信頼できない入力がその処理に到達し得るか。
- ベンダーが提供する修正や緩和策は何か。
- 仮に悪用された場合、どのデータやサービスに影響するか。

たとえばMicrosoftの.NET向けアドバイザリでは、Brotli展開が既定で自動的に行われるかどうかなど、利用経路に関する条件が説明されている。同じ「Brotliを含む」という事実でも、具体的な露出は構成によって異なる。

しかし、到達可能性が未確認だから安全と判断してよい、という話ではない。今回のように悪用が報告されている問題では、影響確認と並行してベンダーの更新情報を追い、可能な修正・緩和策を速やかに進める必要がある。

脆弱性情報を見つけるだけでは対応は終わらない。システムの依存関係と境界を把握し、判断の根拠を残すところまでが重要だ。

## だったら、防御も開発初日から始めよう

ここからは開発側の話だ。

これまでの現場では、機能実装を優先し、CI/CDやセキュリティチェックは仕上げの段階で整備する、という進め方もあったと思う。もちろん、継続的インテグレーション自体は以前からある考え方で、最初から実践しているチームも多い。

それでも、プロジェクトの立ち上げ時にはやることが多い。テスト環境を用意し、ビルドを自動化し、依存関係を整理し、実行権限を設定する。小規模な開発ほど「まず動くものを作ってから」と判断されやすい。

ところが今は、AIコーディングエージェントに、プロジェクトの技術スタックに合った最小限のCIを組み立ててもらえる。設定ファイルの作成だけでなく、失敗したビルドの原因調査や、テスト実行方法の整備まで支援してもらえる。

AIを使う価値は、機能を早く実装できることだけではない。品質と安全性を継続して確かめるための初期コストも下げられることだ。

だから、機能を作り終えてからCI/CDを追加するのではなく、最初の機能に着手する前後に、小さなCIを置いておきたい。

## Day 0 CIは、小さくていい

ここでいう「初日からCI/CD」は、最初から本番デプロイまで完全自動化することではない。

まずは、最小の検証パイプラインを用意する。例えば次のような構成だ。

| タイミング | 最初に確認すること | 開発とともに育てること |
| --- | --- | --- |
| Day 0 | ビルド、Lint、最小のテスト、Secrets混入対策、依存関係の把握 | 必要なチェックを実行できる土台 |
| 機能実装 | 単体テスト、重要な契約テスト、PRごとの検証 | 機能と検証をセットで増やす |
| コンポーネント結合 | 実コンポーネントでの主要な結合テスト | 認証・認可、状態遷移、主要異常系の確認 |
| リリース | 成果物の確認と承認付きデプロイ | 運用に必要な確認やロールバック手順 |
| 運用 | 依存関係の更新・脆弱性アラートの確認 | 新しいリスクを継続的に評価する |

GitHubであれば、CodeQLの既定セットアップやDependency Reviewなど、既存の機能を活用できる。Dependency ReviewはPRで新たに導入される脆弱な依存関係を確認するもので、既存依存関係の継続監視とは役割が異なる。これらの機能が使える範囲は、リポジトリの公開状態や契約プラン、利用する言語などにも左右される。

重要なのは、テストの件数やCIのジョブ数を増やすことを目的にしないことだ。

まだ存在しない機能のために巨大なFixtureや複雑なテスト基盤を作る必要はない。まずはビルドが壊れたことに気づけるだけでも価値がある。コンポーネント間の契約が決まったら、それを検証するテストを足す。外部公開するAPIができたら、必要な認証・認可の検証を足す。

機能と一緒に、品質とセキュリティの検証を育てる。それでいいと思う。

なお、CDはCIと区別したい。本番環境への自動配信まで初日から必要とは限らない。デプロイ先や権限境界を早めに考えつつ、実際の公開・反映には承認を設けるなど、リスクに合わせて段階的に導入すればよい。

## CI/CD自体も、守る対象になる

少し皮肉なのだが、セキュリティを高めるために導入したCI/CDそのものが攻撃対象になることもある。

ワークフローはコードを実行し、依存パッケージを取得し、ときにはリポジトリやデプロイ先への権限を持つ。設定を誤れば、機密情報の漏えいや不正な変更につながりかねない。

GitHubのセキュリティガイドでも、`GITHUB_TOKEN` の最小権限、信頼できないコードの扱い、外部Actionの依存関係管理などが推奨されている。

AIにワークフローを生成させるなら、少なくとも「動くこと」だけでなく、何にアクセスできるか、何を実行するか、どの変更を誰が承認するかを確認したい。

そして、CIのチェックがすべて緑色でも「完全に安全」という意味ではない。検出できない脆弱性もあるし、設定ミスや運用上のリスクも残る。CIは安全の証明書ではなく、検証の証拠を積み上げるための仕組みだ。

## RDADとも、つながっている

以前、[AIコーディングエージェントによる過剰実装と統合テストの手戻り](/posts/rdad-origin/)をきっかけに、[RFC-Driven Agentic Development（RDAD）](/posts/rdad-introduction/)という開発原則を考えた。

RDADで重視するのは、コンポーネント間の契約を事前に確認する Contract First、必要十分なものを作る Minimal Sufficient Implementation、重要なリスクを検証する Risk-Based Verification、そして受入条件と結果で完了を判断する Evidence-Based Completion などだ。

Day 0 CIは、この原則を実際の開発に落とし込むための、自然な実践方法だと思う。

RFCで受入条件と重要なセキュリティ要求を決める。予備設計で信頼境界やコンポーネント間の契約を確認する。実装計画では、機能の実装順序だけでなく「いつ、何を自動検証するか」も決める。

そして、実装の最初から小さなCIを回し、必要な検証を段階的に追加する。

これなら、最後の統合テストで初めて大量の問題に気づく状況を減らせるかもしれない。もちろん、どの程度の効果があるかは、実際のプロジェクトで測定する必要がある。

次の記事では、RDADにDay 0 CIをどのように組み込むか、具体的な開発フローとGitHub Actionsの構成を考えてみたい。

## おわりに

AIによって、脆弱性の意味を理解し、探し、対処するためのハードルは変わり始めている。

その変化は攻撃側だけのものではない。防御側にも、これまで後回しにしがちだった取り組みを初期から始める余地が生まれている。

セキュリティを、完成後に受ける最後の検査ではなく、開発中ずっと確かめ続けるものにしたい。

AIがコードを書く速度を上げたのなら、コードの品質と安全性を確かめる速度も上げなければならない。

そして、そのための最初の一歩は、案外小さくていい。

> **Security should start with the first commit, not the final release.**
>
> セキュリティは、最後のリリースではなく、最初のコミットから始めよう。
