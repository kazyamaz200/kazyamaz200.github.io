[前回の記事](/posts/mlpa-rdad-v02-from-idea-to-experiment/)では、「ロボット同士が短いメロディーで話せたら面白い」という思いつきを、RFC、予備設計、実装計画へ落とし込むところまでを書いた。

そのとき、MLPA（Melodic Language for Physical AI）は、まだ最初の実装に着手したばかりだった。

そこからCodexでWP00〜WP07の8段階を進め、音声を使った2つの仮想エージェントの会話、人間による試聴評価、そしてPoCの最終受入まで到達した。

先に結果を書くと、事前に定めた**A1〜A9の9つの受入条件は、最終的にすべてPass**となった。ただし、実マイクやスピーカーで会話したわけでも、実機ロボットで動作させたわけでもない。無雑音の合成音声を使う、限定した研究PoCでの結果である。

そして今回、いちばん振り返りたいのは「完成した」という事実だけではない。

**初回テストが通ったとき、通らなかったとき、そして数値上は合格しているのに受入を止めたとき。RDAD v0.2の契約と証拠が、それぞれどう使われたのか。**

## 8つのWPで、何を少しずつ増やしたのか

今回適用した[RDAD v0.2](/rdad/)では、RFCで「何を成功とするか」、予備設計（PD）で「どういう約束で成立させるか」、実装計画（IP）で「どの順に確かめるか」を整理してから実装に進んだ。

MLPAでは、次の順序で、毎回新しいリスクを一つずつ増やしていった。

| 作業     | その段階で確かめたこと                            | 結果                                     |
| -------- | ------------------------------------------------- | ---------------------------------------- |
| **WP00** | 意味から一文を作り、同じ意味に戻せるか            | Day 0の9テストが初回成功                 |
| **WP01** | 語彙と文法で、作例以外の組合せを表せるか          | 承認済み30意味ケース一致                 |
| **WP02** | 文を記号的な旋律へ変え、元へ戻せるか              | 30意味・ヘッダー一致                     |
| **WP03** | 合成した音声サンプルだけから意味を復元できるか    | 30意味一致、Profile C2選定               |
| **WP04** | 2エージェントが許可要求・応答・確認を完了できるか | 最初の3発話の会話が成立                  |
| **WP05** | 拒否・待機、再送・重複、翻訳と異常系を扱えるか    | 3会話・12発話、修正2サイクルで正式S4受入 |
| **WP06** | 人間にどう聞こえるか、短さはどうか                | 正式試聴と効率評価を実施                 |
| **WP07** | 受入条件と証拠の対応は本当に妥当か                | 監査とオーナー承認を経て最終受入         |

最初に音声処理から作らなかった理由は、問題の切り分けを容易にするためだった。

WP00で一文、WP01で文法の組合せ、WP02で音符の表現、WP03で実際の音声、WP04で最小の会話。こうしておけば、たとえば音から意味を戻せないときに、文法の問題なのか、符号の問題なのか、音響検出の問題なのかを追いやすい。

最初の実体会話も、すべての異常系が完成するまで待たなかった。WP04では「要求 → 許可 → 確認」のC01だけを先に通し、WP05で拒否・待機・復旧へ広げた。

## WP00〜WP04は、選定した検査窓で初回全件成功

結果として、WP00〜WP04の代表的な検査窓は、いずれも初回に予定したテストがすべて成功した。

特にWP01では、WP00の製品コードを修正することなく、承認済みの30意味ケースを往復できた。WP02では文枠と音型、WP03では音声サンプルへの変換と復元を追加し、WP04では音声を経由して相手が次の発話を決める会話まで進んだ。

もちろん、**「初回成功が続いた」ことと、「RDADのおかげで成功した」ことは違う**。

作業ごとに難易度も試験範囲も分母も異なる。同じ課題をRDADなしで実装した比較結果もない。契約と作業分割が役立った可能性はあるが、その効果量を数字で示せる段階ではない。

それでも、最初の一文を実体で確認してから徐々に境界を増やしていく進め方は、実行可能だった。ここまでは、観測された事実として書ける。

## WP05で、ようやく手戻りが見えた

RDADの実践という観点で、今回もっとも面白かったのはWP05だった。

許可だけでなく、拒否、待機要求、発話の重複、聞き取れない音声、再送の予算まで扱うようになると、個々の処理が正しくても会話全体の状態が食い違う可能性が増える。

正式な統合検証は、次のように進んだ。

| 検査窓     | 結果        | 何が起きたか                                                               |
| ---------- | ----------- | -------------------------------------------------------------------------- |
| **S4-W01** | **294/296** | 順序違反の扱いと日本語訳の正解Fixtureに誤りを検出                          |
| **S4-W02** | **296/296** | テストは全件成功。しかしログ監査で、予約した再送が実送信されない経路を発見 |
| **S4-W03** | **297/297** | 送信予約・期限・実送信の関係を修正し、検証を1件追加して最終受入            |

W01で見つかった一つ目の問題は、要求履歴のないACKという**順序違反**を、音声の**復号失敗**と同じ修復経路へ渡していたことだった。本来は不正な順序として拒否すべきなのに、余計な再送要求（REPEAT）を生成してしまう。

もう一つはテスト用の正解データの問題で、翻訳Fixtureの左右が逆になっていた。テストの失敗が、製品コードではなく**期待値の誤り**を教えてくれた。

この二つを見直した後、W02では296件すべてが成功した。

ところが、そこで終わらなかった。

応答の配送欠落を再現したE04のログを詳しく見ると、**再送を予約した直後に期限処理が走り、実際に送信する前にFailedへ移行していた**。テストの終了結果だけでは、設計上期待した「再送を実行してから失敗終了する」振る舞いを十分に確認できていなかった。

そこでFIFOキュー、期限、再送予算の境界を見直し、「再送予約」だけでなく**実送信したこと**まで確かめる検証を追加した。最終的にW03は297/297で成功した。分母が1件増えたのは、検証を追加したためだ。

ここで得た教訓は単純だ。

**テストが全部通ったことと、期待した契約が十分に検証されたことは同じではない。**

RDADのContract FirstとRisk-Based Verificationは、今回、何がおかしいのかを見つけるための物差しになった。しかも、初回の294/296も、中間の296/296も消さずに残した。最終成功だけを見せて「最初から順調だった」とはしない。

## 人間には、ちゃんとメロディーに聞こえるのか

MLPAは音で情報を伝えるだけでなく、人間にも短いメロディーとして聞こえることを狙っている。

WP03で自分が予備試聴した段階では、音の印象はイメージに近かった。ただし、開発者自身が良いと感じたことは、正式な音楽性評価にはならない。

そこでWP06では、固定した6つの意味ケースそれぞれに、MLPA音声と比較用の不規則音列を用意した。同じ音色、長さ、音数、休符構造にそろえ、条件の正体を知らせずに人間に評価してもらった。

最終的に採用したのは**5名（うち非開発者2名）からの60音声評定**。各音声について、メロディーらしさ・自然さ・不快さを5段階で評価した。

| 指標の中央値           |  MLPA | 比較用の不規則音列 |
| ---------------------- | ----: | -----------------: |
| メロディーらしさ       | **4** |                  2 |
| 自然さ                 | **3** |                  2 |
| 不快さ（低いほど良い） | **1** |                  2 |

事前に定めた条件は、「MLPAのメロディーらしさ・自然さが各3以上」「メロディーらしさが比較音列より高い」「不快さが3以下」という4つ。最終的な評価では、いずれも満たした。

ただし、5人による探索的な結果である。多くの人に普遍的に好まれると証明したわけでも、統計的な優越を実証したわけでもない。参加者の再生機器や聴取環境による違いも残る。

そして、この結果を**そのまま最終受入にしてよいか**という問題が、次のWP07で現れた。

## WP07では、数値が合格していても一度止めた

WP07で音楽性の集計を独立に計算すると、中央値は再現できた。数値基準は満たしていた。

一方で、追加参加者に割り当てた試聴順と、回答時の参加者番号との対応が、当初の記録からは十分に追えなかった。また、空欄だった2つの評価が後に「メロディーらしくなかった」という評点1として扱われていたが、**それが回答者本人の訂正なのか**は、記録だけでは確定できなかった。

「判断できない」と「メロディーらしくない」は同じ意味ではない。事前に定めた欠測の扱いを、後から都合よく変えることもできない。

そのため、WP07では**A7をいったんBlocked**にした。

変更前のデータや、確認できる回答だけを用いた感度分析でも数値閾値自体は満たしていた。しかし、それだけで「所定の手順どおり試聴された」とは言えない。**計算が再現できることと、元の評価が妥当な手順で得られたことは別**だからだ。

その後、オーナーが、追加参加者には試聴前に既存の提示順を割り当てていたこと、同じ固定音源を使用したこと、2つの評点は参加者本人の回答を伝えた訂正だったことを確認した。元の空欄も、途中の分析データも、Blockedの判定も残したまま、事前の尺度・受入基準を変更せずにA7をPassへ更新した。

最後にPoC全体の受入は、オーナーが別途承認した。

これは今回の**Evidence-Based Completion**をもっともよく表した場面だったと思う。

「合格と出たから完了」ではなく、「その合格を判断する根拠は揃っているか」を確かめる。必要な根拠が欠けていれば止め、確認できたら進める。判断に至った経緯も消さない。

逆に言えば、**参加者と提示順の対応、欠測の理由、本人訂正を試聴時点で記録できていれば、後から確認する手間は減らせたかもしれない**。これは次回の改善点として残った。

## RDAD v0.2の6原則は、どう現れたか

今回の実践を、RDADの6原則に対応させると次のようになる。

| 原則                                  | MLPAで見えたこと                                                                                      |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Contract First**                    | RFCの受入条件をPDの責務・異常系、IPの検証ケースにつないだ。順序違反と復号失敗を区別する基準にもなった |
| **Minimal Sufficient Implementation** | 最初は一文、次に記号、音声、C01の会話と、必要な縦断経路だけを実装した                                 |
| **Risk-Based Verification**           | 黙示的な許可、ACKの履歴、重複適用、再送・期限といった失敗時に危険な境界を重点検証した                 |
| **Complexity Budget**                 | Python標準ライブラリと既存の検証入口を再利用し、汎用音響基盤や実機接続は作らなかった                  |
| **Bounded Iteration**                 | WP05では原因と境界を見直し、2修正サイクルで収束した。ただし反復上限の有効性までは検証していない       |
| **Evidence-Based Completion**         | 初回失敗、中間成功、追加監査、オーナー確認を残し、A7の保留から最終受入までを追跡した                  |

とくにv0.2で強化したDay 0の検証基準とVerification Provenance（検証証拠の来歴）は、今回の流れと相性がよかった。

正解データの承認、音響Profileの選定、テストの初回結果と再実行結果、試聴回答の原本と訂正――これらを別々に保持していたからこそ、どの結果を再利用できて、どこで追加確認が必要なのかを判断できた。

一方、ログやハッシュ、検査窓を整理する負担があったのも事実だ。必要十分な証拠量は、今後も調整が必要だと思う。

## 「速くなった」とは、まだ言わない

今回の実装は、体感としては驚くほどテンポよく進んだ。実際に各WPでは目標メーターの時間・トークン量や時計の観測を残している。

ただし、記録された時計の一部分を足して総開発時間にすることはできない。レビュー・試聴の待機時間、人間の実作業時間、エージェントの純実行時間は、同じ定義で測定できていない。目標メーターのトークン量も課金API量と同一とは確認できていない。

さらに、**同じ条件でRDADを適用しない比較実験をしていない**。この事例から「開発時間が何％短縮した」「手戻りが何倍減った」といった改善率は算出できない。

今回、実際に確認できたのは次のことだ。

- 段階ごとの検証条件を定義して、PoCを最終受入まで進められた。
- 途中の失敗と修正内容を、最終成功で上書きせず追跡できた。
- テストの全件成功後にも、必要な契約や評価の来歴を追加で監査できた。
- オーナーの判断が必要な場面では、受入を保留してから再開できた。

それ以上の生産性の効果は、次の比較実験に持ち越す。

## 次に変えるなら、開発フローより「判断の記録」から

今回の振り返りで、次に優先して改善したいのは、文書を増やすことよりも**外部から得た証拠の扱い**だ。

人が関わる評価では、匿名参加者番号だけでなく、どの試聴順をいつ割り当てたか、何を配布したか、空欄がどう訂正されたかを発生時点で記録する。テストでは成功・失敗だけでなく、契約が要求する実送信や状態遷移まで確認する。Fixtureの独立性も、左右や否定、履歴文脈のような間違えやすい意味の照合まで含める。

これらは次の実践で試したい改善候補であって、まだRDAD v0.3の仕様が確定したという話ではない。

## おわりに

「ロボット同士がピロピロと話せたら面白い」。そこから始まったMLPAは、限定したPoCの中で実際に音を出し、二つのエージェントが要求・応答・確認を交わせるところまで到達した。人間の試聴でも、事前に決めた探索的な基準を満たした。

そして、RDAD v0.2についても、一つの実験を最初から最後まで通してみることができた。

今回の学びは、**RDADが失敗をなくしてくれる、ということではない。失敗の場所を確かめ、修正の理由を残し、受入に必要な証拠を問い直せることに価値がある**、ということだった。

AIコーディングエージェントに「作って」と言えば多くのコードができる時代だからこそ、何をもって成功とするか、何を確かめて完了とするかは、ますます大切になるのかもしれない。

もちろん次は、実マイクやスピーカー、雑音や残響のある環境も気になる。でも、それはまた別の研究課題として、次のRFCから考えてみたい。
