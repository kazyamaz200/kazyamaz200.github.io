_— RDAD v0.1の実測結果と考察_

AIコーディングエージェントに開発を任せていると、実装そのものよりも、統合テストでの手戻りに時間を取られることがある。

実装が過剰になったり、コンポーネント間の認識が揃わなかったり、テストの失敗を修正し続けてなかなか完成しなかったり。

そんな経験から考えたのが、[RDAD（RFC-Driven Agentic Development）](https://gist.github.com/kazyamaz200/94595a2045a9562b9c804c17780fede9#file-rdad-md)という開発原則だ。

今回、RDAD v0.1を実際の開発に適用し、7段階の既存システム改修を最後まで進めることができた。

せっかくなので、実行記録を振り返りながら、何がうまくいき、何が課題として残ったのかを整理してみたい。

## 1. 何をしたのか

今回の対象は、複数のプログラミング言語やコンポーネントで構成された既存システムだ。

機能追加だけでなく、既存のデータ形式、状態管理、異常時の復旧、システム間連携などを含む改修を、7段階の優先順位に分けて進めた。

使用した環境は次のとおり。

| 項目                     | 内容                                                      |
| ------------------------ | --------------------------------------------------------- |
| コーディングエージェント | Codex                                                     |
| 使用モデル               | GPT-6.1 Sol                                               |
| 推論設定                 | 中（Medium）                                              |
| 開発原則                 | RDAD v0.1                                                 |
| 開発対象                 | 既存システムの7段階改修                                   |
| 評価対象                 | 受入完了、統合テスト、修正サイクル、契約・Fixture、実行量 |

RDADは、RFC（Request for Comments）から予備設計、実装計画、実装、統合検証、完了判定へ進む開発方法論だ。

特に、コンポーネント間の契約を先に確認する **Contract First**、同じ修正を延々と繰り返さない **Bounded Iteration**、検証結果を根拠に完了を判断する **Evidence-Based Completion** を重視している。

優先順位1の途中からRDAD v0.1を適用し、その後は基本原則を変更せずに7段階の検証を進めた。

なお、人間が工程間の確認や重要な判断を行い、各実装目標の内部をエージェントへ任せる形を取っている。すべてを無人で実行したわけではない。

## 2. 結果

まず、各段階の記録を整理してみる。

| 優先順位 | 記録された時間 | 結果                          |
| -------- | -------------: | ----------------------------- |
| 1        |        約2時間 | 変更受入完了                  |
| 2        |   約11時間12分 | 変更受入完了                  |
| 3        |    約4時間50分 | 変更受入完了                  |
| 4        |   約29時間19分 | 最終検査5/5が初回成功         |
| 5        |    約90時間8分 | 初回4/7 → 最終7/7             |
| 6        |   約15時間13分 | 固定入力後95/95起動が初回成功 |
| 7        |     約8時間5分 | CI最終成功、変更後の受入完了  |

※時間は各段階の報告値・目標メーターに基づく参考値。順位1〜3は以前の概算報告、順位4は最終報告の概算、順位5〜7は目標メーターの記録を用いた。計測方法が完全に統一されているわけではなく、人間の作業時間やプロジェクト全体の経過時間を表すものではない。

最も時間がかかったのは優先順位5で、約90時間8分だった。

一方、優先順位6は約15時間13分で、多数の対象へ展開する作業を完了している。

ただし、各段階の作業量や難易度は異なるため、単純な時間比較で効率を評価することはできない。

統合テストの結果も興味深い。

優先順位4では、開発途中に契約の見直しや修正が繰り返されたものの、最終形式の検査は5/5で初回成功した。

優先順位5では、最終照合の初回成功は4/7。修正を重ねて7/7に到達した。

優先順位6では、実行前に入力や契約を照合し、最終段階の95起動がすべて初回成功した。

そして優先順位7では、CIで失敗と修正を繰り返し、さらに終盤で受入範囲を変更したうえで、変更後の条件を満たして完了した。

**7段階すべてで定義された受入範囲に到達したものの、その過程は決して一様ではなかった。**

また、優先順位7では正式リリースや実機での受入を後続工程に移しており、今回の完了は製品全体の正式公開を意味しない。

## 3. 考察

今回の検証から、特に三つのことを感じた。

### 契約を先に考えることには意味がある

複数のコンポーネントを変更するとき、各コンポーネントの内部だけを正しく実装しても、全体が動くとは限らない。

実際、今回も既存の契約やFixtureの不整合が繰り返し見つかった。

一方、優先順位6では、実行前に入力や契約を確認し、問題を切り分けてから統合検証へ進むことで、最終段階の実行が安定した。

もちろん、これだけでRDADによる改善効果を証明できるわけではない。

それでも、**実装後に境界の問題を発見するより、実装前や統合前に確認する方がよい**という設計方針を支持する観察だった。

### 失敗をなくすより、失敗から抜け出すことが重要

RDADを使っても、テストが常に初回成功するわけではなかった。

優先順位5や7では、実際に複数回の修正が必要になっている。

しかし、繰り返す失敗に対して、同じ場所を修正し続けるのではなく、契約やFixture、実行環境などへ調査範囲を広げることができた。

これはBounded Iterationで意図した振る舞いに近い。

**大切なのは修正回数をゼロにすることではなく、失敗の原因を見直し、完了へ向けて収束させること**なのだと思う。

### 完了の定義は、思っていた以上に重要

優先順位7では、終盤で受入条件を変更した。

ここでは、延期した作業を完了したことにはせず、変更後の範囲と検証結果を明確にして完了を判断した。

現実の開発では、途中で要求や優先順位が変わることもある。

だからこそ、**何を完了とし、何を後続へ引き継ぐのかを明示すること**が重要になる。

Evidence-Based Completionは、単にテストを通すための原則ではなく、そうした判断のためにも役立つと感じた。

### 開発効率は改善したのか

ここは、二つの観点から考えたい。

まず、**人間が実装・検証を行う従来の開発と比較した場合**だ。

これは、体感としては劇的に改善している。

複数の言語やコンポーネントにまたがる改修を、人間がすべて調査し、実装し、統合テストを繰り返していたら、相当な時間が必要だったと思う。

今回、長いものでは約90時間に及ぶエージェントの実行があったが、それは人間が90時間ずっとコードを書いていたという意味ではない。

人間は要求や設計の確認、重要な判断、結果の受入に集中し、実装と検証の多くをエージェントへ任せることができた。

この働き方の変化による生産性の向上は、実際に開発を進めた立場として強く感じている。

一方、**その改善のうち、RDAD自体がどれだけ寄与したのか**については、まだ定量的に評価できていない。

RDADを使わない場合との同条件の比較実験は行っておらず、各段階の作業量も異なる。

また、目標メーターのトークン使用量から、アカウント全体の利用枠消費や課金額を直接比較することもできない。

つまり、今回の結果は次のように整理できる。

**AIエージェントを活用することによる人力開発からの効率改善は、実感として非常に大きい。RDADについては、その高い実行能力を、手戻りを抑えながら受入完了へつなげるための方法論として、一定の手応えが得られた。**

ただし、その効果を数値として切り分けるには、今後の比較検証が必要だ。

## 4. RDADの改善に向けて

今回の結果を踏まえ、次のRDAD v0.2では、特に既存システムへの適用方法を改善したいと考えている。

第一に、**Contract Firstを、既存契約の発見から始めること**。

既存システムでは、コードやテストの中に、ドキュメントに書かれていない前提が残っている。

そのため、As-Is（現状）、To-Be（変更後）、Contract Delta（契約の差分）、Impact Map（影響範囲）を明確にする方法を検討している。

第二に、**修正が繰り返されるとき、コンポーネントを横断して原因を見直すこと**。

失敗したテストだけを直すのではなく、前提となる契約や他の利用側まで調査する。この判断を、より具体的な開発手順にしたい。

第三に、**検証結果の記録方法を統一すること**。

今回の初回成功率は、ケース、バッチ、実行回数、CIなど、段階によって集計単位が異なっていた。

今後は、初回成功、最終成功、修正回数、実行時間、トークン数を、比較可能な定義で記録できるようにしたい。

加えて、**人間が開発へ関与した時間**も測定してみたい。

AIの総実行時間だけでなく、人間が要求を整理し、判断し、問題を調査し、受入を行った時間を記録できれば、実際の開発効率をより正確に評価できるだろう。

そして、今回のような受入条件の変更についても、変更理由と未完了範囲を追跡できる形を整えたい。

RDAD v0.2は、こうした改善を検討している段階であり、まだ有効性を検証したわけではない。

## おわりに

今回の7段階改修では、AIエージェントを活用することで、人間だけで進める場合とは大きく異なる開発の進め方を実現できた。

一方、RDADがすべての問題を防いだわけではなかった。

設計漏れもあれば、Fixtureの不整合もあり、統合テストでの手戻りもあった。

それでも、要求と契約を確認しながら実装を進め、失敗の原因を見直し、検証結果を根拠に各段階の完了まで到達できた。

**RDADは、AIに失敗させないための方法論というより、失敗しても正しく完成へ向かうための方法論なのかもしれない。**

今回の結果を一つの基準として、次はRDAD v0.2の有効性も確かめていきたい。
