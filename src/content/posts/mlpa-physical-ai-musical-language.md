ロボット同士が会話するとしたら、どんな声が聞こえてくるだろう。

人間のように日本語や英語を話す必要は、必ずしもない。相手がAIであるなら、人間に向けた発音や語彙に合わせる理由もないはずだ。

では、ロボット同士が短いメロディーで会話していたらどうだろう。

「ピロピロ」「ピロリン」と音を交わしている。周囲の人には小さな音楽の掛け合いに聞こえるけれど、当のロボットたちは「今、ここを通ってもいい？」「作業中だから少し待って」「了解」と話している。必要なら、そのやり取りを日本語に翻訳して確認できる。

そんな思いつきから、**MLPA（Melodic Language for Physical AI）** という人工言語を考え始めた。

まだ仕様も実装もない、アイデア段階の話だ。今回は、何を作りたいのか、既存の技術と何が違うのか、どうすれば小さく試せそうかを整理してみる。

## 音を使って通信することと、音で言葉を話すこと

AI同士が音で通信する試みは、すでに存在している。

たとえば[**GibberLink**](https://github.com/PennyroyalTea/gibberlink)は、AIエージェント同士が会話相手もAIだと認識すると、人間の音声会話から音響データ通信へ切り替えるデモだ。使われている[**ggwave**](https://github.com/ggerganov/ggwave)は、音を介して小さなデータを送受信するためのライブラリである。

これらは大いに参考になる。ただ、今回作りたいものは少し違う。

任意のデータを音に変換して送るだけなら、それは音響モデムに近い。MLPAで目指したいのは、**音の並びそのものに、単語や文法としての役割を持たせること**だ。

たとえば「許可」「移動」「あなた」「右側」「完了」といった概念を組み合わせ、あらかじめ登録されていない文章を作れる。受信側はその音を復号するだけでなく、文として解釈する。

音を通信媒体にすることと、音を言語にすること。その違いを、MLPAの出発点にしたい。

## 先輩にあたる音楽言語、Solresol

調べてみると、19世紀にはすでに似た発想があった。

[**Solresol（ソルレソル）**](https://www.babbel.com/en/magazine/what-is-solresol)は、フランソワ・シュドルが考案した人工言語で、ド・レ・ミ・ファ・ソ・ラ・シという7音を組み合わせて語彙を作る。単なる音の符号表ではなく、文法を備えた言語として設計されている。

音楽の音を使って意味を伝える、という着想自体は決して新しくないわけだ。

一方、Solresolは人間が使うことを想定した言語だった。MLPAが想定する話者は、スピーカーとマイクを持ち、音程や長さを機械的に制御できるフィジカルAIである。

だから、発音のしやすさや人間の記憶しやすさより、**機体間での認識精度、文法の再現性、翻訳可能性、聞いていて不快でないこと**を重視する設計もできるかもしれない。

もちろん、それらが同時に成立するとは限らない。音楽らしさと通信の堅牢さの両立は、これから検証すべき課題だ。

## 自然言語に近い体系を持たせたい

MLPAを「音を鳴らすコマンド体系」で終わらせないためには、少なくとも三つの要素が必要だと思う。

**語彙**。移動、観測、待機、物体、位置、時間、許可、否定などの基本概念を表すもの。

**文法**。誰が、何を、誰に対して、どんな条件で行うのか。疑問、否定、条件、完了といった関係を表す規則。

**会話**。呼びかけ、返答、確認要求、聞き直し、会話終了など、複数の発話をつなぐ仕組み。

まずは、五音音階のような限られた音の集合から始めてみたい。たとえば、ド・レ・ミ・ソ・ラ。音の組み合わせを語の材料にし、休符や決まった音型を区切りに使う。

ただし、五音音階を採用すれば必ず美しく聞こえるわけでも、正しく聞き取れるわけでもない。使う音域、発音時間、音量、部屋の残響や雑音に大きく左右されるだろう。

最初は音程に語彙を担わせ、文法を固定語順や独立した機能語で表す方がよさそうだ。疑問文を必ず上昇音型にする、といった音楽的な文法は、その後に検証すればいい。

### たとえば、こんな会話

2台のロボットが、狭い通路で出会ったとする。

**Robot A**：「あなたの右側を通過してもいいですか？」

**Robot B**：「今は作業中です。少し待ってください。」

**Robot A**：「了解しました。待機します。」

それぞれの文章が、短いメロディーとして発声される。

この段階では、具体的な音符と単語の対応はまだ定義しない。最初に作りたいのは、次のような**言語として表現すべき意味の構造**だ。

```yaml
# MLPAの内部意味表現のイメージ（仕様未確定）
speaker: robot-a
sentence: question
predicate: pass
actor: robot-a
reference: robot-b
relation: right-of
modality: request-permission
```

この意味表現を語彙と文法で文章にし、さらに旋律へ変換する。受信側では逆順に解釈する。こうすれば、人工言語としての設計と、音を正確に届けるための設計を分離できる。

## フィジカルAIに「声帯」を後付けする

もう一つ、MLPAで実現してみたいことがある。

**異なるロボットに、後付けできる人工声帯モジュールを作ること**だ。

人間が言葉を話すとき、脳内で考えている内容と、声帯を使った発声の仕組みは同じものではない。MLPAでも、ロボット本体の判断と、言葉を組み立てて音にする仕組みを分けたい。

構成としては、次のようになる。

```text
Physical AI（認識・判断・行動）
            │
            │ 意味・意図
            ▼
     MLPA Vocal Module
       ├─ Language：語彙・文法
       ├─ Encoder：意味 → 文章 → 旋律
       ├─ Decoder：旋律 → 文章 → 意味
       ├─ Dialogue：会話状態の管理
       └─ Translator：人間向け翻訳
            │
       スピーカー / マイク
            │
         空間中の音
            │
     別のMLPA対応機体
```

ロボット本体は、相手に伝えたい意味をMLPAモジュールへ渡す。モジュールが文章を作り、短い旋律として発声する。受信側のモジュールはそれを解釈し、ロボット本体へ意味を返す。

「声帯」と呼んでいるけれど、実際には声と耳、そして言語処理の一部をまとめた装置に近い。最初はソフトウェアとして作り、うまくいけば小型コンピューター、マイク、スピーカーを使った独立モジュールにしてみたい。

音色を機体ごとに変えられたら、ロボットに声の個性も生まれるかもしれない。ただし、音色が変わっても言語の意味が変わらない設計が必要になる。

## 人間に読めなくても、翻訳できるようにする

MLPAを人間が耳で理解できる必要はないと思っている。

しかし、**人間が意味を確認できない言語にはしたくない**。

人工言語として語彙と文法が定義されていれば、会話内容を日本語や英語に翻訳する道がある。例えばロボットたちが「ピロピロ」と会話する横で、管理用の画面に次のような字幕を表示する。

> Robot A：右側の通行許可を要求しました。
>
> Robot B：作業中のため待機を要求しました。
>
> Robot A：要求を確認し、待機を開始しました。

これは音声認識AIにメロディーの意味を推測させるのとは違う。文法に従って復元した意味構造から、人間向けの文章を生成する仕組みを目指す。

もちろん、翻訳には情報の省略や言い換えが生じる。安全や監査に関係する場面では、訳文だけでなく元の意味構造と受信結果を残すべきだろう。

## 音楽であることに、どんな意味があるのか

ロボット同士の通信だけなら、Wi-FiやBluetoothなどを使う方法もある。MLPAがそれらを置き換える必要はない。

それでも、音を使うことには独特の魅力がある。

同じ空間にいる機体が、そこにあるマイクとスピーカーでやり取りできること。周囲の人も、何かが話されていることを耳で感じられること。そして、その音が警告音や電子的な雑音ではなく、短い音楽のように聞こえること。

言語としての正確さに加えて、**人間とロボットが同じ空間で過ごすときの音の風景**も設計対象にできる。

ただし、音は壁や反射の影響を受け、録音・再生もできる。聞こえたからといって近くにいることや送信元が本物であることは保証されない。複数機体が同時に話せば衝突も起こるし、繰り返されれば音楽的なメロディーでも騒音になり得る。

まして、移動や接触を伴うフィジカルAIの安全判断を、受信した旋律だけに委ねるべきではない。送信元認証やリプレイ攻撃（録音・再生によるなりすまし等）への対策に加え、障害物検知、衝突防止、緊急停止は独立した安全機構として持つ必要がある。

音楽的に聞こえることと、信頼できる通信であることは別の問題だ。

## 最初は2台のPCで十分かもしれない

いきなりロボットに搭載するより、まずは小さな実験で言語としての成立性を確かめたい。

最初の目標は、**2台の端末がMLPAで短い会話をし、第三者の画面に人間向けの翻訳を表示できること**だ。

順番としては、次のように考えている。

1. **言語の試作**：20〜50程度の基本概念と、疑問・否定・条件などの最小文法を定義する。最初は音を使わず、文章の生成と解析をテストする。
2. **旋律への変換**：限られた音階で発声・受信する。意味構造から旋律へ、旋律から意味構造へ、往復できるかを確認する。
3. **会話の成立**：2台の端末で要求・回答・確認・聞き直しを実装し、翻訳画面を追加する。
4. **人工声帯化**：スピーカーとマイクを備えた小型モジュールへ移植し、異なる機体への組み込み方法を検討する。

評価したいのは、文章を正しく復元できる割合、雑音や距離に対する強さ、発話時間、複数話者の干渉、そして人間にどう聞こえるかだ。

音響通信の比較対象にはggwaveが使えるだろう。MLPAが既存の通信方式より高性能だと決めつけるのではなく、**言語としての表現力と、音楽としての聞こえ方を追加することで何を得て、何を失うのか**を見てみたい。

## おわりに

フィジカルAIが普及したとき、異なるロボットがどうやって意思疎通するのかは、きっと重要なテーマになる。

その方法が、人間の声に似ている必要はない。

短い旋律を語彙として持ち、文法に従って言葉を作り、周囲の機体と会話する。人間には意味が分からなくても、必要なら翻訳できる。そして、ロボットにその声を後付けできる。

**MLPA — Melodic Language for Physical AI。**

まだ、作れるかどうかも分からないアイデアだ。でも、フィジカルAIに声帯を与えてみるという発想から、言語学、音楽、音響通信、ロボティクスが一つにつながってきた。

まずは、2台の端末が短いメロディーで会話できるところから試してみたい。
